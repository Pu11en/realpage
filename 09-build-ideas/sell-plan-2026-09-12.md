# What are we selling? — planning brainstorm (2026-09-12)

Status: brainstorm in progress. No code changes. Drew's answers get added below as we go.

## Plain facts: what RealPage is

- RealPage sells **software to companies that own or manage apartment buildings** (landlords with hundreds or thousands of units).
- The software runs the building's business: leasing, rent collection, pricing rents, resident apps, accounting.
- Their rivals sell the same kind of software: **Yardi, Entrata, AppFolio, MRI, Buildium**.
- So RealPage makes money by **winning buildings from those rivals** (and keeping its own). Every building runs on one of these systems.
- Public image is bad: the DOJ sued them over their rent-pricing algorithm; Reddit is openly hostile (posts with 15k+ upvotes).

## What PropertyStack already does (the starting point)

- Finds apartment buildings in an area and works out **which of these software systems each one uses**.
- Ranks buildings by early signs they may switch (Early Leads = a call list).
- A chat agent answers questions, does web lookups, and prepares for calls.
- Live on Railway with Google sign-in.

## The one-sentence pitch (draft, to test)

- "PropertyStack tells your sales team **which apartment buildings run a competitor's software, and which ones are likely to switch soon**, with a ready call sheet for each."
- Deliverable = a tool + a weekly ranked call list, not a report.

## Open questions (answered one at a time)

1. ⏳ Who is the buyer: RealPage sales, RealPage's AI team (the interview), rivals' sales, or property managers?
2. ⬜ What does "production-ready to sell" mean for that buyer (copy, onboarding, proof, price)?
3. ⬜ Language check: pull Reddit posts from salespeople and property managers to learn how they talk.
4. ⬜ Easy wins: what can the existing agent add cheaply (call sheets, email drafts, PDFs)?
5. ⬜ Copywriting: headline, 3 benefits, one example, one call to action.

## Answers

### Q1: the buyer (Drew, 2026-09-12)

- Worry: a "call list" is underwhelming. RealPage probably already has lead lists, so why would they want ours?
- Drew's idea: **one agent in the chat that does the whole sales research job, start to finish**:
  1. **Scout areas**: suggests places with untapped opportunity; Drew picks one.
  2. **Build the lead batch**: finds every building in that area and its software (today this only runs on Drew's local harness; move it into the chat agent).
  3. **Rank**: talk with the agent about which buildings to call first.
  4. **Deep dive**: for the top few, the agent researches that one building (Jina web lookups) and writes a brief on *why* they'd switch and what to say.
  5. **Area log**: remembers every area explored, so the coverage map grows over time.

### My take (to test with Drew)

- The new value isn't the list. It's **"an AI sales researcher that works a whole city for you and hands each rep a reason to call."** Lead lists are common; a per-building "why now" brief is not.
- Signals for picking an area: lots of new apartment construction, growing renter counts, many buildings on rival software, recent building sales.
- What a salesperson needs in the brief ("trigger events"): a new owner or new management company (new managers often switch software), a new building in lease-up, resident reviews complaining about the portal or payments, unit count, current software, and who to contact.
- Bonus for the interview: this shows exactly the job skills (agent workflows, tools, logs, human picks the next step).

### Gaps this flow exposes

- 🆕 Four new pieces: scout-areas, run-area (start the pipeline from chat), building-brief, call-kit.
- ⚠️ The chat is read-only today ("must NOT change data"). Step 2 means the agent writes new areas. Probably fine if it only *adds* areas and never edits existing ones.
- ⚠️ Sale and new-construction finders only know Collin County and Plano. A new area needs its own county/city sources, which is the hardest part of "any area".
- ⚠️ Step 2 takes minutes and costs web-lookup credits per building; the chat needs to show progress and cap the size.

### Q2b: scope and how we build it (Drew, 2026-09-12)

- **The flow ends at the call.** Pick who to call → learn about them → call kit. No logging calls, no follow-ups, no CRM.
  - Saving happens automatically anyway: the chat app already keeps each signed-in user's chats (per Google account). The agent has no memory *between* chats, and nothing records areas explored. Fine for now.
- **Build order:**
  1. Build/refine every step as a skill in the **local harness** (Claude Code in this repo, `propertystack/skills/`), not in the chat agent yet.
  2. **Prove the whole flow end to end on one new area** inside a local session.
  3. Only then give the same skills to the chat agent.
- **Architecture rule: kindergarten simple.** One skill = one step = one folder (`SKILL.md` + `run.py`). Each reads only the files before it and writes one numbered file. Same pattern the 7 finder skills already use.
- **Chat agent today (for the gap list):** reads data + research, web search/read, call prep in text, keeps per-user chat history. It cannot: run skills/new areas, write data, make files (PDF), remember across chats.
